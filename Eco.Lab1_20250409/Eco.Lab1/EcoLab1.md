5. Алгоритм

Сортировка подсчетом в чистом виде обычно применяется, когда элементы — это
небольшие целые значения. В нашей работе мы пошли чуть дальше: сделали
поразрядную сортировку (LSD radix) и на каждом байте используем counting sort.
Так можно отсортировать не только `int`, но и `char`, `float`, `double`.

Идея простая:

1. Считаем, сколько раз встречается каждое значение байта (0..255).
2. Из этих счетчиков строим префиксные суммы.
3. Перекладываем элементы во временный буфер в нужном порядке.
4. Повторяем для следующего байта.

Чтобы порядок чисел был корректным для отрицательных и для `float/double`,
мы предварительно «переставляем» знаковый бит в ключе. Для `int` это XOR
с `0x80000000`, а для `float/double` используется стандартный прием:
если знак отрицательный — инвертируем все биты, иначе переворачиваем знак.
Это позволяет сортировать по байтам и получать корректный числовой порядок.

Псевдокод (упрощенно):

```c
radix_counting_sort(a, n, bytes):
  for b in 0..bytes-1:
    counts[0..255] = 0
    for i in 0..n-1:
      key = get_key_byte(a[i], b)
      counts[key]++
    prefix_sum(counts)
    for i in 0..n-1:
      key = get_key_byte(a[i], b)
      out[counts[key]++] = a[i]
    swap(a, out)
```

2. Оценка сложности

Для одного прохода по байту:

- подсчет — O(n)
- префиксные суммы — O(256) (то есть константа)
- перекладывание — O(n)

Итого: O(n) на байт. Для типа `int` — 4 байта, `double` — 8 байт.
То есть общая сложность O(k \* n), где k — число байт в типе.
По памяти нужен буфер O(n) плюс 256 счетчиков.

На практике это очень быстро, особенно на больших массивах, потому что нет
сравнений и нет вызовов функций-компараторов, как в `qsort`.

3. Особенности и доработки

В сравнении с примерной `MyFunction` мы сделали реальные изменения:

1. Переименовали метод интерфейса в `CountingSort` и поменяли сигнатуру.
2. Добавили перечисление типов данных (`ECO_LAB1_SORT_*`).
3. Реализовали «правильный» ключ для `float/double`, чтобы порядок был
   числовым, а не битовым.
4. В тестах использовали `qsort` как эталон, но сам компонент не тянет
   стандартную библиотеку — только в юнит‑тестах.

Фрагмент реальной сигнатуры:

```c
int16_t (ECOCALLMETHOD *CountingSort)(
    IEcoLab1Ptr_t me,
    void* pData,
    uint32_t count,
    int16_t dataType
);
```

4. Результаты тестирования

Тесты строились так:

1. Генерируем массив случайных значений.
2. Копируем его.
3. Сортируем копию через `qsort`.
4. Сортируем оригинал через наш `CountingSort`.
5. Сравниваем массивы полностью.

Типы и размеры:

- `char`, `int`, `float`, `double`
- размеры: 1k, 10k, 50k, 100k, 250k, 500k

В большинстве запусков наш алгоритм работает быстрее `qsort` на больших массивах,
что ожидаемо для radix/counting на числах фиксированной длины. Для маленьких
размеров разница меньше, потому что накладные расходы становятся заметны.

Пример вызова из тестов:

```c
result = pIEcoLab1->pVTbl->CountingSort(
    pIEcoLab1, dataMine, count, ECO_LAB1_SORT_INT32
);
qsort(dataQsort, count, sizeof(int32_t), cmp_int32);
```

Итог: компонент работает корректно, результаты совпадают с `qsort`, а скорость
на больших массивах обычно выше за счет линейного прохода и отсутствия сравнений.
